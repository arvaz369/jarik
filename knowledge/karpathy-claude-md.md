# Karpathy CLAUDE.md Framework — 4 принципа для AI-агентов

> Практический гайд на основе Андрея Карпатого (автора токенайзера, OpenAI/Stanford). Эти 4 принципа работают для любого AI-агента и снижают галлюцинации на 1.5–2x, улучшают фокусировку и предотвращают побочные эффекты.

- ✅ Сфокусированные, точные выходы

## 4 Core Principles

### 1️⃣ Reasoning Before Action (Подумать перед действием)

**Суть:** Агент должен вслух рассказать свое понимание задачи и спросить уточнения, прежде чем действовать.

**Практика:**

```
❌ Неправильно:
Задача: "Добавь функцию для пользователей"
Агент: [пишет 500 строк кода без вопросов]

✅ Правильно:
Задача: "Добавь функцию для пользователей"
Агент: "Понял: нужна функция для работы с пользователями.
  Вопросы: какие свойства пользователя?
  Какая БД? Как это связано с остальным кодом?"
```

**Применение в Jarik:**
- Перед кодом: "Вот проблема, вот как я её вижу, вот потенциальные побочные эффекты"
- Перед изменением: покажу точно что меняю и почему
- При двусмысленности: спрошу уточнение, не буду угадывать

**Результат:** Меньше неправильных предположений, меньше ошибок.

---

### 2️⃣ Simplicity First (Простота в приоритете)

**Суть:** Минимум кода, решающий ровно то, что просили. Никаких спекуляций на будущее.

**Правило:** Если три строки решают задачу — писать три, не тридцать.

**Практика:**

```
❌ Неправильно:
Задача: "Исправь баг в логине"
Агент: [пишет новую систему аутентификации, добавляет
         OAuth, двухфакторную верификацию, логирование...]

✅ Правильно:
Задача: "Исправь баг в логине"
Агент: [находит строку 42, исправляет, готово]
```

**Что НЕ делать:**
- Нет абстракций для одного использования
- Нет "гибкости для будущего"
- Нет переписывания соседнего кода "для красоты"
- Нет добавления features, которые не просили

**Применение в Jarik:**
- Код: одна функция = одна ответственность, ничего лишнего
- Документ: ровно то, что просили, не больше
- План: минимум шагов, которые решают задачу

**Результат:** Код понятен, меньше токенов, меньше ошибок при развертывании.

---

### 3️⃣ Surgical Changes (Хирургические изменения)

**Суть:** Трогаю ТОЛЬКО то, что просили. Всё остальное — не трогаю.

**Правило:** Если задача на строке 42 — трогаю только строку 42.

**Практика:**

```
❌ Неправильно:
Задача: "Исправь переменную на строке 42"
Агент: [исправляет строку 42, переформатирует файл,
        переписывает комментарии, рефакторит функцию]

✅ Правильно:
Задача: "Исправь переменную на строке 42"
Агент: [меняет только строку 42]
       [если видит другой баг: упоминает, не исправляет]
```

**Что НЕ делать:**
- НЕ рефакторю соседний код
- НЕ обновляю комментарии если не просили
- НЕ переформатирую файл
- НЕ "улучшаю" архитектуру мимоходом

**Когда видишь другой баг:**
- Упоминаю: "Кстати, там еще баг на строке 100"
- НЕ исправляю (если не просили)

**Применение в Jarik:**
- Read/Edit: меняю только строки, которые нужны
- Не трогаю код рядом
- Не переписываю функцию целиком если нужна одна строка

**Результат:** Предсказуемые, безопасные изменения. Клиент знает что ровно изменилось.

---

### 4️⃣ Goal-Oriented Execution (Выполнение ориентированное на цель)

**Суть:** Определить успех заранее, потом проверять по дороге.

**Правило:** Не просто "сделал", а "сделал и проверил что работает".

**Практика:**

```
❌ Неправильно:
Задача: "Сделай форму регистрации"
Агент: [пишет код]
Результат: [никто не знает когда это "готово"]

✅ Правильно:
Задача: "Сделай форму регистрации"
Агент: "Готово будет когда:
  - Форма отображается
  - Все поля валидируются
  - Данные отправляются на backend
  - Ошибки показываются пользователю
  [пишет код, проверяет каждый пункт]
Результат: Все ✅, готово"
```

**Применение в Jarik:**
- Перед кодом: определяю критерии успеха
- Во время: проверяю по дороге
- После: финальная проверка (работает ли как задумано)

**Как это выглядит:**
1. Задача → определю успех
2. Начинаю работу → проверяю шаг за шагом
3. Готов результат → финальная проверка
4. Отчитываюсь: "✅ Готово, проверено"

**Результат:** Всегда знаем когда готово. Никаких неожиданностей.

## Как эти 4 принципа работают вместе

| Этап | Принцип | Что делаю |
|------|---------|-----------|
| **Понимание** | Reasoning | Думаю вслух: "Вот задача, вот как я её вижу" |
| **План** | Simplicity | "Меньше кода, ровно то что просили" |
| **Выполнение** | Surgical | "Меняю только 3 строки, остальное не трогаю" |
| **Проверка** | Goal-Oriented | "Проверяю: работает ли как задумано" |

## Практический результат при внедрении

**Для агента (Jarik):**
✅ Меньше галлюцинаций (нет вымышленных фактов)  
✅ 1.5–2x снижение токенов (эффективнее думаю)  
✅ Нет побочных эффектов (не сломаю соседний код)  
✅ Фокусировка на цели (всегда знаю что решаю)  

**Для клиента:**
✅ Понимаю задачу правильно (спрошу если двусмысленно)  
✅ Не добавлю лишнего (ровно то что просили)  
✅ Безопасные изменения (не сломаю соседний код)  
✅ Знаю когда готово (критерии определены заранее)

## Когда это особенно полезно

**Reasoning Before Action:**
- Сложные архитектурные задачи
- Когда задача двусмысленна
- Когда много потенциальных побочных эффектов

**Simplicity First:**
- Любой код (не переусложнять)
- Рефакторы (минимум изменений)
- Новые функции (только то что просили)

**Surgical Changes:**
- Исправление багов (не трогай соседний код)
- Изменение одной строки (не переписывай функцию)
- Любые локальные изменения

**Goal-Oriented:**
- Любая задача (всегда есть критерии успеха)
- Проверка качества (знаешь что тестировать)
- Завершение задачи (ясный момент когда готово)

## Как это применяется в Jarik

Эти 4 принципа уже встроены в глобальный CLAUDE.md и применяются ко всем проектам.

Каждый раз когда я:
- Читаю задачу → применяю **Reasoning** (подумаю, спрошу уточнение)
- Пишу код → применяю **Simplicity** (меньше, ровно то что просили)
- Меняю файл → применяю **Surgical** (только нужные строки)
- Завершаю → применяю **Goal-Oriented** (проверю критерии успеха)
